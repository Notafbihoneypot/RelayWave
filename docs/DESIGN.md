# RelayWave design notes: accounts, storage, migration, pricing

Status: proposal, November 2026. Nothing in this document is implemented unless it says so. It records the direction agreed during the security review so that later work has something to be checked against.

Guiding constraints, in priority order:

1. RelayWave never holds personal information: no email, phone, name or card data.
2. RelayWave never holds a user's private key in a form it can read.
3. A creator can always leave, with listeners following, without asking permission.
4. The price is competitive with ordinary podcast hosts.

## 1. Accounts and login

Two separate things are easy to conflate. Keeping them apart is what makes the rest work.

| | Identity | Account number |
| --- | --- | --- |
| What it is | A Nostr key pair | A random number, Mullvad style |
| What it does | Signs episodes, feed claims, API requests | Holds paid time and the storage quota |
| Who generates it | The user's browser or signer | The server |
| What the server stores | The public key only | A hash only |
| If it leaks | Attacker can publish as the creator | Attacker can spend the creator's paid time |
| If it is lost | See "Lost key" below | Replace it with a backup code |

### Identity

- **New users:** the browser generates a key and shows it once as a 12-word phrase (NIP-06). It also offers a passphrase-encrypted file (NIP-49, `ncryptsec`). The user confirms they saved one of the two before continuing.
- **Existing Nostr users:** connect a signer. Browser extension (NIP-07) and Android signer (NIP-55) exist today; remote signers (NIP-46) should be added.
- The server authenticates every write with a signed NIP-98 event, as it does now.
- The server-side demo key behind `TEST_MODE` must not exist in any build that is reachable from outside a LAN.

### Account number

- Generated by the server, shown once, never emailed.
- Use at least 128 bits of entropy. Mullvad's 16 digits are about 53 bits, which is only safe behind online rate limiting. This number is a bearer credential and should stay safe even if the database leaks, so store only a hash of it.
- One account number can be linked to several public keys (several shows, or a team).
- Linking a key to an account requires a signature from that key.

### Backup codes

- A small set of single-use codes, shown once at signup, stored hashed.
- A backup code replaces a leaked or lost **account number**. It does not and cannot recover a Nostr key.
- The signup screen says this in plain words. There is no support channel that can undo a lost key, and pretending otherwise would require holding the data this design refuses to hold.

### Lost key

Open decision. Two options:

- **A. No recovery.** A lost key means the show can no longer be updated under that identity. Simple and honest. The creator starts a new identity and uses the exit redirect (section 4) to move listeners.
- **B. Account-number re-pointing.** The account number may move a show to a new public key, after a waiting period (for example 14 days) and a public notice on the show's page and feed. This makes recovery possible, and it also makes the account number as powerful as the key.

Recommendation: B, with the waiting period, because losing a show permanently to a lost phone is the more likely failure for real creators than account-number theft.

### Payments

- Prepaid time, no automatic renewal, nothing stored that needs renewing.
- Monero and Lightning keep personal data out entirely.
- Card payments, if ever added, put personal data at the processor. That is a deliberate exception to constraint 1 and should be labelled as one at checkout.
- Do not claim Monero payments work until they have been tested end to end.

## 2. Storage scope

### What is stored

- Audio, artwork, transcripts and chapter files. No video in the first version.
- Check the declared type against the file's actual leading bytes on upload.
- Media is public and content-addressed. Nothing uploaded is private, and the upload screen should say so.

### Limits

- Per-file cap of roughly 300 to 500 MB. The test stack currently allows 2 GB.
- Per-account quota set by the plan, enforced before the upload is accepted (Blossom BUD-06, `HEAD /upload`).
- Only public keys linked to an account with paid or trial time may upload. **Today any Nostr key can upload**, which must be fixed before the Blossom port is reachable from anywhere untrusted.
- Hash large files in chunks in the browser instead of reading the whole file into memory.

### Abuse

Public, content-addressed storage will be abused. Before opening uploads:

- Implement the Blossom report endpoint (BUD-09).
- Keep a blocklist of hashes that are refused on upload and on mirror.
- Write down a takedown process and who carries it out.

### When paid time runs out

- Feed and media stay up for a grace period (suggested: 30 days).
- After that, media is deleted. The feed URL keeps answering with the creator's chosen redirect, or a minimal "this show has moved or ended" feed, for at least 12 months.

### Cost scale

- 128 kbps audio is about 58 MB per hour. A weekly one-hour show is about 3 GB a year.
- 10,000 downloads of a one-hour episode is about 576 GB of transfer. Transfer, not storage, is the cost that grows.
- The project avoids a Cloudflare dependency, so "free egress" offers that rely on it do not apply. Budget transfer explicitly when choosing where media lives.

## 3. Moving a show in

1. **Identity.** Create or connect a Nostr key.
2. **Prove control of the existing feed.** The creator adds a one-time code to the old host as a channel-level `<podcast:txt purpose="verify">` element. Implemented today in `features/feed-claims.mjs`. Transistor and RSS.com document a field for this tag; whether Yellowball exposes one has not been confirmed and should be checked first, since the test feed lives there.
3. **Fallback proof.** Where a host has no such field, accept the code placed temporarily in the channel description. Record which method was used; treat this one as weaker.
4. **Respect `podcast:locked`.** If the feed says `yes`, stop and tell the creator to unlock it at the old host. Not implemented today.
5. **Bind the claim to the show, not the URL.** Key verified claims on the channel's `podcast:guid` when present. Today claims are keyed on the exact URL string, so the same feed at a slightly different URL is a separate claim.
6. **Claims expire.** Re-verify periodically and let a creator release a claim. Today the first claimant holds a URL forever.
7. **Private import.** Copy episodes with channel GUID, episode GUIDs and publication dates unchanged. Copy media into Blossom and record each hash. Show the creator a comparison of old and new feeds. Nothing is public yet. Not built.
8. **Cutover.** The creator sets a 301 redirect at the old host to the new feed. The new feed carries `itunes:new-feed-url` pointing at itself as a backup. Keep both for at least four weeks. RelayWave never redirects a feed it does not host.

The interface must not describe import as available until step 7 exists.

## 4. Leaving

The exit has to be as easy as the entrance, and it has to keep working after the creator stops paying.

- **Redirect out.** A "Leave" page where the creator enters the new feed URL. RelayWave answers the old feed URL with a 301 and adds `itunes:new-feed-url`. Kept alive at no charge for at least 12 months.
- **Media.** One action mirrors every file to another Blossom server (BUD-04) and publishes the creator's server list (kind 10063), so apps can find the same hashes elsewhere. A plain download of all files is also offered.
- **Feed.** The RSS feed is standard and can be imported by any host. `podcast:locked` is the creator's switch, off by default.
- **Own-domain feed address.** Let creators serve their feed from a domain they control. This is the strongest exit, because listeners never subscribe to a RelayWave address in the first place. Yellowball already offers it.
- **Identity.** The Nostr key and everything signed with it were never RelayWave's to keep.

## 5. Competitors and pricing

Prices were gathered in November 2026 from search summaries and third-party trackers, several of which disagree. Confirm on each host's own pricing page before relying on a figure.

| Host | Entry paid price | Metered by | Notes |
| --- | --- | --- | --- |
| Yellowball | $7/mo; $3/mo archive | Upload hours | Free tier: 2 h/month, kept 90 days. Unlimited shows, free imports, own-domain feed |
| Buzzsprout | $12 to $18/mo | Upload hours | Free tier: 2 h/month, kept 90 days |
| RSS.com | about $15 to $20/mo | Unlimited audio | Repriced during 2026 |
| Podbean | $9 to $12/mo, annual | Unlimited audio | |
| Libsyn | $7 to $12/mo | Upload volume | |
| Captivate | $17 to $19/mo | Downloads | |
| Transistor | $19/mo | Downloads | |
| Fountain for Podcasters | $25/mo; $50 Pro | Per podcast | Closest rival: RSS, Lightning and Nostr |
| Spotify for Creators | Free | Nothing | Takes 50% of dynamic ad revenue |

Proposed starting point, to be tested against real transfer costs:

- **Free:** ownership check and private import preview.
- **One flat plan, about $5/month:** prepaid, with a monthly upload-hour allowance.
- **Archive, $2 to $3/month:** keeps a finished show online with no new uploads.

What RelayWave offers that the table does not: no email at signup, an ownership proof signed by the creator's own key, and an exit that is guaranteed after payment stops. No host above combines all three.

## 6. Open decisions

1. Lost-key policy: no recovery, or account-number re-pointing with a waiting period (section 1).
2. Whether card payments are ever accepted, given constraint 1.
3. Where media lives in the distributed version, and who pays for transfer.
4. The flat price, once transfer cost per show is measured.
5. Who handles takedown reports, and how they are reached without collecting reporter data.
